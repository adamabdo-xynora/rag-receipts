## What was measured

Every chunk was scored against every question: 71 × 14 = 994 cosine similarities against
live `voyage-4` embeddings. Each score was then labelled by the committed ground truth in
`eval/questions.json`: **correct** if the chunk is one the question's answer requires,
**wrong** otherwise. No generator was called and no threshold was applied — the run
measures the score landscape the floor has to cut through, it does not run the pipeline.

## Why 0.4364

The two kinds of wrong retrieval are not the same failure:

- **A wrong chunk retrieved for an answerable question is a precision cost the pipeline
  absorbs downstream.** The gate allows extra citations, and the verifier still requires
  the expected chunks and byte-exact quotes. All five of the highest-scoring wrong
  chunks above belong to answerable questions; admitting them wastes context, it does
  not produce a wrong answer that survives verification.
- **A wrong chunk retrieved for a must-refuse question is the only route to a headline
  failure.** It is what puts material in front of a generator for a question the corpus
  cannot answer. Nothing downstream can undo that — the refusal path depends on the
  generator never being called.

So the soundness constraint is not the naive separation (which does not exist); it is
the **must-refuse ceiling**. The floor must sit strictly between:

- **0.3622** — the best score any chunk achieves against a must-refuse question
  (`saturday-delivery-surcharge` vs `rush-and-same-day-orders#rush-surcharge`), and
- **0.5106** — the worst correct retrieval
  (`join-zone-c-freight-820` vs `wholesale-pricing-and-minimums#free-freight-thresholds-by-zone`).

Any floor inside that band keeps every required chunk retrievable and starves the
generator on every question the corpus cannot answer. **0.4364 is the midpoint** —
equidistant from both measured failure boundaries rather than tuned toward either,
because at n=15 correct retrievals no point inside the band is more defensible than any
other. The residual naive overlap (wrong chunks between 0.4364 and 0.5843 that clear the
floor) is a precision cost, not a soundness one.

## What the old 0.35 was doing wrong

The previous `MIN_SIMILARITY = 0.35` was a documented guess, and it sat **below** the
measured must-refuse ceiling of 0.3622. Concretely: the `rush-and-same-day-orders#rush-surcharge`
chunk, at 0.3622, was clearing the floor for the Saturday-delivery question — a
must-refuse question — and reaching the generator. The guess failed in exactly the
unsafe direction its own comment warned against. The constant was moved to 0.4364 in a
separate reviewed commit to `src/retrieve.ts`, where the derivation now lives beside it.

## What this run does NOT establish

No generator was called. Nothing here measures answer quality, citation behaviour, claim
verification against live output, or the gate verdict — the demo's generator responses
remain hand-written fixtures, and no model has answered a question in this repository.
What this run establishes is exactly one thing: the retrieval floor is now measured
against the live embedder it applies to, instead of guessed. The pipeline end-to-end
has not yet been run against a live model; that is `npm run eval` without `--calibrate`,
and it has not happened.

A calibration run also does not move the constant by itself: the artifact records
`currentThreshold: 0.35` — the value at the time of the run — and says so, because the
floor is a property of the embedding model and moving it is a reviewed commit, not a
side effect of a measurement.
